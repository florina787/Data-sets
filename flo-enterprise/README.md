and the answer arrives as a live dashboard with evidence-cited actions and human approval gates.</h3>

> [!IMPORTANT]
> **Independent architecture demonstration.** It is not affiliated with any asset manager, bank or advisory firm, uses no
> protected branding and has no access to proprietary systems. **All data is synthetic** (fixed seed), **all integrations
> are mock adapters**, the default model is a **deterministic in-process mock** (no external LLM calls), and **securities
> trading is prohibited**. Recommendations are prompts for human review, not advice.

## 1. Why FLO

Most AI dashboards stop at activity: tokens, tasks and uptime. People who run an investment business ask different
questions, and FLO answers them before showing anything else.

| | The question | How FLO answers |
|---|---|---|
| 01 | *What happened to our money?* | Deterministic `Decimal` engine. AUM reconciled to the cent; revenue split exactly into volume, mix and fee effects. |
| 02 | *Why did it change?* | Specialist agents explain drivers from governed facts. Every number in the narrative must be found in those facts. |
| 03 | *What happens if…?* | Scenario and sector-shock engines with stated assumptions. Outputs are labelled conditional, never forecasts. |
| 04 | *What should we do?* | Prioritized actions that cite their evidence, with owner, KPIs, validation criteria and dependencies. No invented ROI. |
| 05 | *Which decisions need a human?* | Client letters, personalized advice, board distribution and exports are paused at hash-bound approval gates. |

Three design rules run through everything:

<table>
<tr>
<td width="33%" valign="top"><h4>Numbers are computed once</h4>
The LLM never calculates. One engine feeds every KPI, chart, narrative and export, and numeric grounding rejects any
figure not in the governed facts.</td>
<td width="33%" valign="top"><h4>Follow the real work</h4>
Progress, agent timelines and evidence come from events the backend actually emitted, never simulated activity. Each
tool call is authorized for the signed-in user and audited.</td>
<td width="33%" valign="top"><h4>Humans decide</h4>
Consequential actions need an authorized human. Approvals are bound to the exact payload, single-use, expiring and
re-authorized at execution. There is no trading capability at all.</td>
</tr>
</table>

## 4. How a question flows

```mermaid
flowchart LR
  U["Composer"] -- "POST …/messages/stream<br/>(Server-Sent Events)" --> I["Intent planner<br/>flo-intent-rules/1.0<br/>+ conversation state"]
  I --> P["Policy check<br/>identity, not persona"]
  P --> G["LangGraph<br/>guard → supervisors → specialists"]
  G -- "every tool call" --> GW{{"Tool gateway<br/>RBAC · ABAC · audit"}}
  G --> V["Visualization agent<br/>allowlisted chart builders"]
  V -- "data fetched as the user" --> GW
  G & V --> R["Recommendation engine<br/>evidence-cited · roadmap"]
  R --> X["Numeric grounding<br/>+ schema validation"]
  X --> S[("Conversation store<br/>entity ids only · PII masked")]
  X -- "stage · plan · agent · result" --> U
```

```mermaid
sequenceDiagram
  autonumber
  participant B as Browser
  participant A as API (SSE)
  participant O as Orchestrator
  participant G as Tool gateway
  B->>A: message + idempotency key + context (months, scenario, client id)
  A-->>B: started {request_id}
  O->>O: classify intent, resolve references from conversation state
  A-->>B: stage understanding ✓ · stage permissions ✓ (agents permitted for this identity)
  O->>G: specialists call governed tools as the user
  A-->>B: agent events as each specialist finishes (with its tool calls)
  O->>G: visualization agent fetches chart data as the user
  A-->>B: stage visualization ✓ · stage validation ✓ (grounding, evidence on every action)
  A-->>B: result {MessageResponse flo.conversation/1.0}
  Note over B,A: Dropped connection? Re-post with the same key:<br/>the server joins the in-flight run and returns its stored result
```

| Capability | How it works |
|---|---|
| **Streaming** | Server-Sent Events with real `stage`, `plan`, `agent`, `result` and `error` events, plus keep-alives. |
| **Cancellation** | **Stop** calls an owner-only cancel endpoint. The harness and gateway check cancellation between steps, and a cancelled result is stored truthfully. |
| **Retries and reconnection** | Every message carries an idempotency key. Duplicates run once, concurrent retries wait for the original, and a broken stream falls back to the JSON endpoint with the same key. |
| **Partial results** | Denied agents or withheld charts produce `partial` with explicit warnings. A missing client id produces `needs_input` with the user's own clients to choose from. |
| **Persistence** | Conversations and messages in PostgreSQL/SQLite (migration `0004`): searchable history, user text PII-masked at rest, owner-only access (others get 404). |

## 5. Conversational memory

Follow-ups keep context as **ids and parameters**, never as stored values, and every reuse goes back through
authorization.

| You say | FLO resolves | What runs |
|---|---|---|
| “Show our portfolio performance.” | intent `portfolio_performance` | performance agent → trend, period comparison, sector contribution |
| “Compare it with last quarter.” | *it* = the previous analysis · *last quarter* = 3-month window | same agent, `months=3`, vs the preceding 3 months |
| “Which sector contributed the most?” | focus `sector_contribution`, window kept | headline names the top contributor; the sector is saved as an entity |
| “What happens if *that sector* falls 15%?” | *that sector* = Information Technology · shock −15% | sector-scenario agent → impact by mandate, product AUM and fee revenue |
| “Break this down by product.” / “Now show the last 24 months.” | modifiers on the previous intent | same agents with `group_by` or `months` |
| “What happens if rates rise by 200 basis points?” | scenario with `rate_shock_bps=200` | scenario agent; follows on from an earlier scenario if there was one |

If a client is reassigned after a conversation, reloading it **withholds** the stored answer, and a follow-up about that
client is **denied**. Both behaviours are tested.

## 6. Agents and orchestration

```mermaid
flowchart LR
  Q[/"Message + context"/] --> G["guard<br/>size · injection scan · language"]
  G --> ES{"enterprise<br/>supervisor"}
  ES --> EX["executive"] & IN["investment"] & WE["wealth"] & RC["risk & compliance"] & AO["AI operations"]
  EX -- "Send() fan-out<br/>independent tasks only" --> S1["aum"] & S2["financial performance"] & S3["revenue"]
  IN -.-> S4["performance · scenario · sector shock · portfolio · benchmark"]
  WE -.-> S5["client · wealth · retirement · meeting · retention · products"]
  S1 & S2 & S3 & S4 & S5 --> SY["synthesize"]
  SY --> VZ["visualization agent"] --> RE["recommendations + validation"] --> E((answer))
```

**25 specialist agents plus the visualization agent**, each with a full contract (owner, version, roles, tool allowlist,
input/output schema, budget, data classification, approval and evaluation requirements):

| Domain | Agents |
|---|---|
| Executive | AUM · Financial Performance · Revenue · Board Reporting · Decision Memory · Advisor Productivity · Firm Diagnostic (prospects) |
| Investment | Portfolio · Performance · Benchmark · Investment Research · Market Intelligence · Scenario · Sector Scenario |
| Wealth | Client Intelligence · Wealth Advisor · Retirement Planning · Product Research · Client Meeting · Client Retention |
| Risk and compliance | Risk · Compliance Research |
| AI operations | Operational Intelligence · Data Quality · Evaluation |

Every specialist runs through the **harness** (role admission, schema validation, budgets, deadlines, retries, circuit
breakers, cancellation, numeric grounding). It reaches data only through the **tool gateway**, which checks for an unknown
tool, a prohibited action, the agent's allowlist, strict arguments, the policy decision for the human principal,
approval obligations and rate limits, and audits each call. Full table: [docs/AGENTS.md](docs/AGENTS.md).

## 7. Charts and the visualization schema

```mermaid
flowchart LR
  T["Tool output<br/>(authorized for the user)"] --> B["Allowlisted builder<br/>e.g. performance_trend"]
  B --> S["ChartSpec flo.viz/1.0<br/>type · data · units · metric defs · lineage · provenance"]
  S --> V{"Server validation<br/>allowlisted type · shape · finite · ≤5,000 points"}
  V -- ok --> R["Browser maps data → ECharts<br/>(no code executed)"]
  V -- invalid --> X["rejected"]
```

* **18 declared chart types**: line, area, stacked area, bar, horizontal bar, stacked and grouped bar, combo, waterfall
  (revenue bridge), donut, treemap, heatmap, correlation matrix, scatter, geographic map, tornado, scorecard and agent graph.
* **Every chart** offers tooltips, drill-down (click → a follow-up question), filters as pill toggles, table view,
  PNG/CSV export, *Explain with FLO*, methodology, source lineage, data freshness and a provenance badge.
* **Design language.** Near-black tiles with a glowing gold-to-lime hero line, fading area fills, near-invisible grids, a
  rounded tooltip with a crosshair, a headline value with a change pill, rounded bar tops and sparkline KPI tiles.
  Animations respect `prefers-reduced-motion`.
* **Authorization first.** A chart whose data the user may not see is withheld and audited, and never rendered from cached
  or elevated data. Composition skips charts the identity can't use; the gateway still decides every call.

## 8. Recommendations: facts, interpretations, simulations, actions

Each answer separates what is **observed**, what it **means**, what is **simulated**, and what is **proposed**:

| Section | Meaning | Example |
|---|---|---|
| Observed facts | computed from governed data | “AUM is CAD 50.81bn, up 3.08% over 12 months” |
| Analytical interpretation | what the facts indicate | “Operating margin fell from 30.69% to 27.85%” |
| Simulated outcomes | conditional on stated assumptions | “If Information Technology fell 15%, portfolios would lose about CAD 15.1m” |
| Risks · opportunities · limitations | context and caveats | “Sector contribution is a holdings-based approximation” |
| **Proposed actions** | prioritized; each needs a human decision | “Run an expense-growth review led by technology” (P1, Finance, 0–30 days) |

Every proposed action carries its **evidence** (agent and fact), rationale, expected benefit (described, not
estimated), KPIs to track, complexity, dependencies, owner, timeframe, required approvals and validation criteria.
The schema has **no field** for ROI, probability, confidence or expected return, so none can be invented. A tested rule
enforces that. Roadmaps sequence actions into 0–30, 31–60 and 61–90 day phases with governance gates.

## 9. Governance and security

```mermaid
flowchart LR
  REQ["request(principal, action, resource, context)"] --> A{authenticated?}
  A -- no --> D1["DENY · AUTHN-REQUIRED"]
  A -- yes --> B{prohibited?<br/>trade · shell · raw DB}
  B -- yes --> D2["DENY · PROHIBITED-ACTION"]
  B -- no --> C{RBAC grant?}
  C -- no --> D3["DENY · RBAC-DENY-DEFAULT"]
  C -- yes --> T{same tenant?}
  T -- no --> D4["DENY · TENANT-ISOLATION"]
  T -- yes --> X{ABAC<br/>assignment · clearance · segregation · residency}
  X -- fail --> D5["DENY · rule id"]
  X -- pass --> OB{approval-gated?}
  OB -- yes --> AP["ALLOW with obligation<br/>approval_required"]
  OB -- no --> OK["ALLOW"]
```

```mermaid
stateDiagram-v2
  [*] --> pending: request (requester authorized)
  pending --> approved: approver confirms payload hash (not self, right role, same tenant)
  pending --> rejected
  pending --> expired: TTL
  approved --> executed: re-authorize · hash matches · single use
  approved --> invalidated: payload changed after approval
  executed --> [*]: replay rejected
```

| Control | Implementation |
|---|---|
| Identity and least privilege | `Principal` propagated API → harness → tools → telemetry. Policy bundle **1.4.0** adds a least-privilege `risk_officer` (aggregate exposure only) and a `prospect` role (conversation plus public data). |
| Policy-as-code | Versioned YAML RBAC/ABAC with a content hash in every decision; Rego mirror with parity tests; OPA sidecar fails closed. |
| Conversation security | Persona never grants access. Stored context is ids only and re-authorized on reuse; stored answers are withheld when access is revoked; other users' conversations return 404. |
| Client-scoped cache | Record-scoped (confidential or restricted) agent outputs are never served from cache, and the policy version is part of the cache key. This bug was found by the conversation tests and fixed. |
| Model providers | Region and classification policy. The optional Gemini provider is approved for **public data only**; the key travels in a header and prompts are PII-masked. |
| Privacy | Detection (SIN with Luhn, accounts, e-mail, phone, DOB, addresses, names, secrets), masking, tokenization, encrypted vault, audited rehydration, retention purge, subject erasure. |
| Prompt injection | Guard scan, quarantine of malicious documents, and a gateway that blocks a compromised plan (export, e-mail, trade). |
| Audit | Append-only SHA-256 hash chain in a separate store, PII redacted, tamper detection tested; every allow and deny recorded. |
| Human in the loop | Comms, personalized recommendations, sensitive exports, board distribution, record changes, portfolio modifications. **No trading capability exists.** |

Details: [docs/SECURITY.md](docs/SECURITY.md).

## 10. Personas: a UX preference, never a permission

| Persona | Shapes the experience | Typical identity |
|---|---|---|
| CEO / Executive Leadership | KPIs first, board language, AUM · margin · revenue bridge | `executive` |
| CFO / Financial Leadership | revenue, expenses, budget variance, methodology shown | `finance` |
| CIO / Investment Leadership | performance, concentration, scenarios | `cio` |
| Institutional Investment Manager | mandates, stress tests, correlation | `cio`, `investment_analyst` |
| Portfolio Analyst | benchmarks, correlation, formulas in methodology | `investment_analyst` |
| Wealth Advisor | client reviews, retirement, suitability screens | `wealth_advisor` |
| Relationship Manager | retention signals in the advisor's own book | `wealth_advisor` |
| Risk and Compliance Officer | exposure, risk register, policy research | `risk_officer`, `compliance_officer` |
| Business Owner / Prospective Client | plain language, glossary, labelled assumptions | `prospect` |
| AI Operations Administrator | agent graph, traces, data quality | `ai_admin` |

An advisor who picks “CEO” still gets an advisor's data. In the test, that request is **denied**, and
`/api/personas` marks which personas match the sign-in.

## 17. Limitations and deployment readiness

**Limitations**

* Synthetic data and mock adapters only; nothing connects to a production system. Figures are illustrative.
* The default model is deterministic templating, so narratives are accurate but formulaic. Bedrock and Gemini adapters
  exist; Gemini is unit-tested against a fake transport, and neither has been evaluated against a live model.
* Intent planning is a deterministic rule set (`flo-intent-rules/1.0`), not a language model; unusual phrasings fall back
  to the supervisor's own routing.
* Sector contribution is a holdings-based approximation. Sector shocks are instantaneous, single-sector and first-order.
* Agent durations are measured from fan-out to completion within one run; repeated identical questions may be served
  from the harness cache and are labelled.
* Mock IdP (HS256 tokens in `sessionStorage`). Approval checkpoints use SQLite. Breakers, the agent cache, in-flight
  request tracking and cancellation handles are per process.
* Regulatory references are illustrative; the AI makes no legal or regulatory determinations.

**Deployment readiness**

| Area | Status |
|---|---|
| Conversation workspace, governed agents, dashboards, approvals, audit | Working; tested end to end against the running app |
| Security controls (RBAC/ABAC, tenant isolation, privacy, injection, cache scoping) | Working; adversarial and regression tests pass |
| Data | Synthetic and badged in every view |
| Integrations (PMS, accounting, CRM, ERP, market data) | Mock adapters behind provider-neutral interfaces |
| Identity | Mock IdP; production needs enterprise OIDC/SSO |
| Scale-out | Needs shared stores for approvals, in-flight tracking and cache; horizontal scaling not measured |
| Infrastructure | Compose verified (1.x); Helm and Terraform validated, **not applied** to a real cluster or account |

**Verdict:** ready to demonstrate and pilot on synthetic or sandbox data; **not** ready for production client data until
SSO, real integrations, shared state for multi-replica deployment, a live-model evaluation and a security review are done.
