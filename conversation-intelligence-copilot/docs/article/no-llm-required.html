No LLM required

How I built an AI copilot that answers contact-centre questions over 3,000 customer conversations, and still gives the right answer with the language model switched off.

By Florina ~18 min read Interactive: try the router, break a float, rank the topics View the code on GitHub

A contact-centre analyst asks a simple question: which topics drove negative sentiment last month? The tempting build is to hand the transcripts to a large language model and print whatever comes back. It reads well. It might also be wrong, in ways no one notices until a leadership deck goes out with a number that never existed.

I have shipped enough analytics to distrust that build. A wrong number in a dashboard is worse than no dashboard, because people act on it. So I built the opposite. The Conversation Intelligence Copilot is an agentic analytics assistant for customer-support conversations. A LangGraph workflow plans the analysis, runs registered DuckDB queries, retrieves the transcripts behind each finding, explains the result and then audits its own answer before you see it. A language model is optional. The four questions this project was built around are answered with model calls.

This article covers how it works, the decisions behind it, and the problems that nearly sank it. Numbers with a yellow marker were computed by the system; hover or tap one to see which operation produced it.

The rule that shaped everything

Before writing any code I wrote one rule and let it decide every later trade-off: numbers are computed, never generated. I wrote it down because I knew I would be tempted later, at the point where a model "almost" gets a count right and it would be so much faster to let it.

Every count, rate and rank comes from one of registered, parameterised DuckDB operations. The model never writes SQL. It never sees a number it could change, because the explanation step is checked afterwards: if the text contains a figure that is not in the verified result, the explanation is thrown away and a deterministic one is used instead.

Once that rule was in place, a second question followed naturally. If the model cannot contribute facts, when is it worth calling at all? I spent more time on that question than on any single feature.

Try the router

The answer is the Zero-LLM router. Before any model is involved, a cascade of cheap, high-precision checks decides what the question is and whether a model would add anything. Type a question below, or pick one. The lab is a simplified copy of the rule stage, running in your browser.

Most analytical questions stop at the second step. A rule recognises the intent, the registered operations compute the full answer, and a model would only add cost and latency. The model is called in two situations. One is when no rule can route the question with high precision. The other is when the question asks for interpretation (why, explain, recommend). Even then it only picks a category from a closed list, or phrases an explanation of numbers that were already computed.

Policy checks run first and always win. Questions that need data the dataset does not have (revenue, CSAT, handle time) or that ask for a personnel decision are refused deterministically. No model is needed to say no.

The whole system, one stage at a time

Every box below is a real LangGraph node. In the app, the nodes light up live as a request runs, and a Decision Replay panel lets you step back through them afterwards. Click a node to see what it does.

Three choices in this graph matter more than the rest.

  • The supervisor plans, it does not compute. It resolves the time window and any references to earlier answers, then picks registered operations. The analytics layer accepts nothing else.
  • Retrieval runs in parallel, and only illustrates. Hybrid search finds real transcripts for the top-ranked result. It never produces a number.
  • Verification is a stage, not an afterthought. The QA agent and the Evidence Challenger run on every answer. More on the Challenger below, because it caught me out.

Question one, answered

The first assignment question asks for the top 5 topics associated with negative sentiment in the last month. "Last month" turned out to be the first trap. The data spans August to early December 2025, so last month means the latest month in the data, not today's calendar. In November 2025, of conversations were negative.

The challenges

None of what follows was in the brief. These are the problems that took the time, roughly in the order I hit them. Open any of them for the details.

01A mean of exactly −0.25, according to a computerlabelling

A conversation counts as negative when the mean sentiment of its customer turns is −0.25 or lower. Conversation C0010797 has eight customer turns. Their mean is exactly −0.25 on paper. In floating point it is not.

The naive mean lands a hair above the threshold, so the conversation was labelled not negative. It changed real answers: a leadership priority score moved from 52.9 to once fixed, and the November negative count went from 239 to .

I found it because one Q4 score in my audit was off by 0.5 and I refused to explain it away. The worse part: I had written an independent checker for the audit, to recompute answers from the raw CSV. It averaged with floats too, so it agreed with the bug. The evaluation oracle now uses exact fractions (Fraction(str(score))), and a regression test pins this exact score pattern.

02Timestamps that are not in turn orderdata

In all conversations, message timestamps do not follow the turn order. Sort by time and a conversation reads as nonsense: answers before questions, thanks before help.

Decision
The turn index is authoritative. Each conversation is dated by its earliest message, and every trajectory answer says that the timestamps were not used for ordering.
03One agent per conversation makes coaching rankings unfairanalysis

Question two asks which agents may benefit from coaching. The data holds agent IDs for 3,000 conversations, with at most 2 conversations each. Any ranking of individual agents would rest on one or two transcripts.

Decision
Say so in the answer, and answer the useful version of the question instead. I would rather tell a team lead "the data cannot support this" than hand them a ranking that could cost someone their job on the strength of two chats.
Result
Workforce-level patterns (only of negative customer turns received an acknowledgement or apology), plus a review queue of conversations with evidence. Every coaching answer is flagged for human review, and requests for personnel decisions are refused.
0441,965 messages, 426 unique textslabelling

The dataset is synthetic. Every message ends with random filler tokens, and once those are stripped there are only distinct message templates. That sounds like a problem. It is also an opportunity.

Decision
Label the 426 templates with a documented rule set instead of labelling 41,965 messages with a model. Sentiment, empathy, courtesy and resolution fit are template-level judgements, written down in ASSUMPTIONS.md.
Trade-off
The labels are my judgement. The app includes a review panel for collecting human labels, and the evaluation says plainly that agreement with humans has not been measured yet.
05The hosted model key was blockedLLM

My plan included a hosted model. The key I had during development returned 401 API_KEY_SERVICE_BLOCKED. This became the most useful constraint of the project, because it forced the question: what does the product actually need a model for?

Decision
Make the model optional everywhere, and add a free local one: Qwen2.5-1.5B-Instruct (Q4_K_M, ≈ 1.1 GB) through llama.cpp on CPU.
Result
The app is fully functional with no model. With the local model, a warm routing call takes about a second. The first call after start-up measured on an idle CPU, and 30 to 55 seconds when other jobs were competing for it.
06A small model routing questions: 19% accurateLLM

My first prompt asked the 1.5B model to classify questions into intents. On a frozen held-out test set it scored . Rewriting the prompt around a closed category list, enforced by a JSON-schema grammar, took it to . Still not good enough to trust.

I could have kept tuning prompts. I decided against it, because a 1.5B model was never going to be reliable at the long tail, and every prompt tweak was a guess I could not verify without spending the test set. The fix was to stop asking the model to do the whole job. A confidence cascade (policy → high-precision rules → semantic match → vagueness guard → model → clarify) lets each stage answer only when it is sure. The chart shows the climb.

Two details I am proud of. The semantic-similarity stage was built and calibrated, and then disabled by its own calibration: no threshold reached 95% precision on validation, so it stays off. And the model is now called for only of test questions.

07The Evidence Challenger corrected my own sentenceverification

The Evidence Challenger is an adversarial check that runs after the explanation is written. It re-reads every quoted excerpt from the database word for word, discloses samples under 30, states counter-evidence ("61% of Item-not-received conversations were not negative"), and rewrites causal wording as association.

When I added the tie disclosure to question one, I wrote that a topic was listed last because of the tie-breaker. The Challenger rewrote "because of" into "associated with" and mangled the sentence. It was doing its job; my wording was the problem. The sentence now reads "The tie-breaker (higher negative rate) lists Login / account locked".

Building it also exposed two real bugs. QA had been reporting "0 evidence items resolved" because the explanation node overwrote the evidence report. And a repeated-phrase detector always returned zero.

08Demo data quietly leaking into the real answersdata

For UI demos I generated 120 tagged synthetic conversations. They were loaded by default, so the dashboard showed 3,120 conversations against an assignment that supplied 3,000.

Decision
Demo data is opt-in (ENABLE_SYNTHETIC_DEMO=true). A default build holds only the supplied data.
Side effect
Removing it changed the lexical index's vocabulary, which moved retrieval scores. The evaluation reports the new numbers and explains the change, instead of keeping the old, slightly better ones.
09Retrieval that is honest about a small gainretrieval

Retrieval indexes four-turn chunks twice: once with MiniLM sentence embeddings and once with LSA (a lexical method). The two rankings are fused with weighted reciprocal rank fusion.

The hybrid wins, but by little, and the fusion weight was tuned on these same queries. The evaluation says both things. A small honest gain is more useful to a reviewer than a large flattering one.

10Token counts that do not lieobservability

Every answer shows its route, how the intent was resolved, and the tokens used. Getting the last one right took more care than expected.

  • Tokens show as 0 (no model call) only when no model was called.
  • When a provider returns no usage data, the UI shows not reported, never a fake zero.
  • Streaming usage is taken as the cumulative maximum, not summed across chunks, which had been double counting.

What it does not do

An honest list, because these are the questions a reviewer should ask.

  • It does not claim cause. The Root Cause Investigator reports tested associations with intervals, separates symptoms (a customer asking to escalate) from candidate drivers, and checks alternative explanations.
  • It does not rank people on thin data. See challenge 03.
  • It has not been validated against human labels. The routing benchmark is 73 questions written by the same person who wrote the rules. The 95.9% is indicative, and the remaining misroutes are listed in the repository.
  • It is not production-hardened. There is no authentication or role-based access, and storage is single-node.

What I would keep

If I started again tomorrow, I would keep three habits.

  1. Write the rule before the code. "Numbers are computed, never generated" settled dozens of later decisions in advance.
  2. Make the model earn its call. A router that can say "no model needed" made the system faster, cheaper and easier to test. It also made the model's genuine contribution measurable: 90.4% without it, 95.9% with it.
  3. Check the checker. The float bug survived an independent recomputation because both used the same arithmetic. Exact fractions in the oracle cost one import.

Run it yourself

No API key, no hosted model. Python 3.12+ with uv, Node 22+ and make:

git clone https://github.com/florina787/Data-sets.git
cd Data-sets/conversation-intelligence-copilot
git checkout claude/happy-edison-gef7ay
cp .env.example .env
make install && make prepare && make index
make dev          # UI on http://localhost:5173

Optional local model: make install-local-llm && make llm-download. VS Code users can open the folder and press F5 on the Full stack launch configuration.
