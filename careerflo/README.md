<summary><b>How one paid action is metered</b> (sequence diagram)</summary>

```mermaid
sequenceDiagram
    participant C as Client
    participant A as FastAPI
    participant M as Metering
    participant F as Feature (agents + MCP)
    C->>A: POST /api/resumes/tailor (Idempotency-Key)
    A->>M: reserve(user, feature, key)
    Note over M: UPDATE … WHERE used + reserved < limit<br/>+ unique reservation row
    alt allowance available
        M-->>A: reservation
        A->>F: run (nested features are included, not charged)
        alt success
            F-->>A: result
            A->>M: commit → used += 1, result cached for replays
            A-->>C: 200 + _usage (1 of 2 free uses remaining)
        else failure
            A->>M: release → nothing consumed
            A-->>C: error
        end
    else exhausted
        M-->>A: FeatureExhausted
        A-->>C: 402 "You've completed your two free trials… Upgrade to continue."
    end
```

## 🎁 Two free uses of every feature

<img src="docs/assets/charts/trials.svg" alt="Seventeen premium features, each with two free uses" width="100%" />

- **Server-side:** the counters live on the server. Logging out or changing email never resets them.
- **Safe under load:** 12 parallel requests still get exactly 2 uses (tested on PostgreSQL).
- **No double charges:** a retry with the same `Idempotency-Key` replays the stored result and isn't charged again.
- **Fair:** a failed run never consumes a use, and a Free plan never auto-charges.
- **Paid plans unlock only from Stripe webhooks.** A checkout success redirect alone never grants access.

## ✅ Tested

<img src="docs/assets/charts/tests.svg" alt="66 backend tests on SQLite and on PostgreSQL, 6 frontend unit tests, 10 browser journeys" width="100%" />

The suite covers all six acceptance scenarios (job discovery, resume optimisation, mock interview, trial exhaustion, Stripe subscription, multi-user isolation). The same journeys also passed locally against the packaged container with **real Qwen3-1.7B on 2 CPU cores**.

## 🕸️ Career Graph: what's true → what matters now → what do I do next

The last page in the app turns your job search into a **semantic spine** of three graphs. Each one is built from your own records, so no model invents a graph fact.

<img src="docs/assets/screens/career-graph.png" alt="Career Graph page: knowledge graph, scoped context graph, procedural graph with the next step, trace and learn, and the semantic spine" width="100%" />

| Layer | Question | What Career_flo builds |
|---|---|---|
| 🟠 **Knowledge Graph** | *What is true?* | Your verified skills, roles, employers, education and certifications, plus the jobs you saved or applied to, their companies, required skills and your recruiter contacts. Every node keeps its **source** (resume, profile, posting, CRM). |
| 🔵 **Context Graph** | *What matters now?* | A small subgraph around **one** target job. It shows required skills split into *have* vs *gap*, the company, recruiters and your application, plus **live state**: match score, posting age, published salary, status, follow-ups due, upcoming interviews. *Don't retrieve everything:* in the demo, 10 of 72 facts are kept. |
| 🟢 **Procedural Graph** | *What do I do next?* | The job search as `(procedure, condition, procedure)` triplets: check fit → close gaps or upskill → tailor → ATS check → cover letter → **your approval** → applied → follow up → interview prep → offer → negotiate. Guards evaluated on the context graph pick the **current step**, explain **why**, and list the possible transitions. It **guides, it doesn't dictate**: steps marked *YOU* always wait for a human. |
| ⚫ **Trace & Learn** | *What worked?* | Success and failure traces from your own history. For example, the demo data shows a **100% response rate with a scheduled follow-up vs 39% without**, alongside your agent runs and approval decisions. |

```mermaid
flowchart LR
    O[Ontology<br/><sub>what things are</sub>] --> K[Knowledge Graph<br/><sub>what's true</sub>] --> C[Context Graph<br/><sub>what matters now</sub>] --> P[Procedural Graph<br/><sub>what to do next</sub>] --> A[AI Agents<br/><sub>act, then write traces back</sub>]
    A -. traces update .-> K
    style K fill:#FFF1E6,stroke:#F59E0B
    style C fill:#EFF6FF,stroke:#3B82F6
    style P fill:#ECFDF5,stroke:#10B981
    style A fill:#F1EEFF,stroke:#7357FF
```

Available as a metered feature (`POST /api/career-graph`, two free uses) and as the MCP tool `analytics.build_career_graph`, so agents reason over the same scoped graph.

## 🚢 Deployment (Hugging Face + low-cost hosting)

```mermaid
flowchart LR
    U([User]) --> S["🤗 Static Space (free)<br/>React build"]
    U --> V
    S -->|HTTPS · VITE_API_URL| V["VPS (same container image)<br/>Caddy → FastAPI + llama.cpp Qwen3-1.7B"]
    V -->|Postgres 5432 + Auth| DB[(Supabase)]
    V -->|test mode| ST[Stripe]
    V -. optional .-> HF["🤗 Inference Providers<br/>Qwen3.5-9B"]
    style S fill:#FFF7E6,stroke:#F59E0B
    style HF fill:#FFF7E6,stroke:#F59E0B
```

**Recommended: hybrid.** The frontend runs on a **free Hugging Face Static Space**. The API and Qwen run in one container on a small VPS, with data and accounts in Supabase. Why not put everything in a Hugging Face Space?
- **Docker Spaces need a paid plan** (PRO, $9/month).
- **Free Spaces sleep** after 48 hours without visitors.
- **Spaces only allow outbound ports 80, 443 and 8080**, so a Space can't reach Supabase's Postgres on 5432/6543.

The all-in-one Space package is still provided (`deploy/hf-space/`), for use if a private test Space confirms database access.

| Usage | Setup | ≈ Monthly cost |
|---|---|---|
| Private test | Static Space + free VPS tier + Supabase Free | $0 |
| Beta (≤ 100 users) | Static Space + 8 GB VPS + Supabase Free | ≈ $10–20 |
| Paying customers | 8 GB VPS + **Supabase Pro** (backups) | ≈ $35–45 |
| Growth (≈ 2,000 users) | + Qwen3.5-9B via Inference Providers | ≈ $45–80 |

Measured on 2 vCPU: one instance serves **about 2 simultaneous model replies**. Ten simultaneous users stay under 0.9 s at p95 on everything else.

**Deploy (each step needs owner approval):** `scripts/hf_deploy.py` stages the build, scans for secrets and **dry-runs by default**. `--apply` creates the Space as private, and `--target static-frontend` deploys the frontend only. `scripts/hf_rollback.py` restores an earlier version. Manual, approval-gated GitHub workflows wrap both.
